# Benchmarks

Reproduce with:

```sh
RUNS=3 scripts/benchmark.sh 2000 500 2000 8000   # main dataset size, then memory-scaling sizes
```

The script generates the datasets under `bench-data/` (git-ignored; the 8,000-file set is ~12 GB), builds in release mode, and prints the tables below. Numbers are from one machine on 2026-10-02.

- Machine: Mac17,2, Apple M5, 10 cores, 32 GB RAM
- OS: macOS 26.6.2; swift-driver version: 1.127.14.1 Apple Swift version 6.2.3 (swiftlang-6.2.3.3.21 clang-1700.6.3.2)
- Dataset: 2000 synthetic JPEGs (2400 px long side, 2.8G total; 80% unique, 10% exact copies, 10% resized near-duplicates), generated by `photosweep-dev make-bench-data`
- Method: release build, median of 3 runs, OS file cache warm (not purged). Wall time is the scan's own timer (discovery through grouping, excluding report thumbnails); memory is peak RSS of the whole process from `/usr/bin/time -l`.

### Cache effectiveness and incremental work (8 workers)

| Scenario | Time (s) | Files decoded | Files hashed | Cache hits |
|---|---:|---:|---:|---:|
| Cold scan (empty cache) | 2.54 | 2000 | 1159 | 0 |
| Repeat scan, nothing changed | 0.10 | 0 | 0 | 2000 |
| Repeat scan after modifying 1% of files | 0.14 | 20 | 14 | 1980 |

### Worker count (cold scan, cache disabled)

| Workers | Time (s) | Speed-up vs 1 | Peak RSS (MB) |
|---:|---:|---:|---:|
| 1 | 14.57 | 1.00x | 53 |
| 2 | 7.40 | 1.97x | 57 |
| 4 | 3.80 | 3.83x | 68 |
| 8 | 2.41 | 6.05x | 86 |
| 10 | 2.11 | 6.91x | 96 |

### Peak memory vs collection size (cold scan, 8 workers, cache disabled, single run)

| Files | Dataset size | Time (s) | Peak RSS (MB) |
|---:|---:|---:|---:|
| 500 | 725M | 0.62 | 78 |
| 2000 | 2.8G | 2.43 | 88 |
| 8000 |  11G | 13.51 | 129 |

## What the numbers show

- **The cache works.** An unchanged repeat scan of 2,000 photos (2.8 GB) takes 0.10 s instead of 2.54 s, decodes no images, and hashes no files. The remaining time is discovery (`lstat` of every file) plus loading and saving the cache.
- **Incremental work is proportional to change.** Modifying 1% of files (20 files) makes the next scan decode exactly those 20 files. Only 14 of them were re-hashed, because only files sharing a byte size with another file need a hash.
- **Concurrency.** Scaling is nearly linear up to 4 workers (3.83×). It flattens after that: 6.05× at 8 and 6.91× at 10, on a machine with 10 cores of mixed performance and efficiency types. The default is `min(cores, 8)`. Each extra worker adds roughly 4–5 MB of peak memory (one decode plus one read buffer in flight).
- **Memory stays bounded.** A 16× larger collection (500 → 8,000 files, 0.7 GB → 11 GB) raises peak RSS from 78 MB to 129 MB. Image data never accumulates. The growth comes from per-file metadata (the file list, cache entries, the manifest) and the report's group structures, roughly 7 KB per file in total at this scale.

## Caveats

- The OS file cache was warm; purging it needs root. Cold-disk times would be higher, mostly for hashing, and would depend on the SSD.
- The data is synthetic: each "unique" image is a zoomed, panned, tinted and noise-added rendering of one of 32 source photos. Many of these renderings are visually similar to each other (the 2,000-file report has 376 visual groups), so visual-group counts here say nothing about matching quality. See [evaluation.md](evaluation.md) for that.
- The 8,000-file row is a single run. The other rows are medians of 3. The 8,000-file scan is slower than linear (13.5 s vs. 4 × 2.4 s); this was not investigated further. Likely causes are a larger share of files needing hashes and less of the 12 GB dataset staying in the page cache.
- Times are the scan's own timer: discovery through grouping, excluding report thumbnail generation. Peak RSS covers the whole process, including report generation.
